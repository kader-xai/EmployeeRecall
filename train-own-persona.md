# Training your own persona model

A practical, end-to-end guide to building an AI assistant that drafts replies in a specific person's writing style and answers "what happened with X?" using their email + meeting history.

> 📝 **Long-form blog post:** [Employee Recall — Capturing a Departing Employee's Writing Style and Memory](https://kader-xai.github.io/posts/employee-recall-lora-rag-persona-continuity/)
> 🎥 **Video walkthrough coming soon** — covers the methodology, training run, and live demos. Subscribe on [LinkedIn](https://linkedin.com/in/kader-m-1a6023a6) to be notified.

This is the same pipeline used to build [`kader-xai/priya-qwen2.5-7b-gguf`](https://huggingface.co/kader-xai/priya-qwen2.5-7b-gguf) from the [`kader-xai/priya-sft`](https://huggingface.co/datasets/kader-xai/priya-sft) dataset. Source code: [github.com/kader-xai/EmployeeRecall](https://github.com/kader-xai/EmployeeRecall).

```
   ├─► prep_training_data.py ──► SFT pairs + RAG chunks + system prompt
   │

   │

```

Wall time: 3–6 hours on a single A100 40GB. Cost: ~$15–25 on RunPod or Vast.ai.

## 0. Before you start: consent and scope

If the person whose voice you're cloning is real, this step is **non-optional**. You need:

1. **Written consent** covering use of their mailbox + meeting archive for an AI assistant.
2. **Data minimization** — strip personal threads, redact PII, financials, HR-sensitive content.
3. **Scope agreement** — model is **draft-only**, never auto-send; every output audit-logged.
4. **Retention policy** — when the model + corpus retire (recommended: 12 months post-departure).
5. **Jurisdictional review** — GDPR, CCPA, India DPDP, HIPAA, GLBA as applicable.

For a synthetic / fictional persona (like Priya in this repo), none of this applies — but call it out clearly in your README so users don't assume it's a real mailbox.

## 1. Define the persona

Create a JSON file describing who they are and how they write. This drives both the system prompt and the data-prep filtering. See [`personas/priya.json`](../personas/priya.json) for a full example. Minimum useful fields:

```json
{
  "id": "priya_sharma",
  "full_name": "Priya Sharma",
  "email": "priya.sharma@northwind-saas.com",
  "role": "Senior Customer Success Manager",
  "tone_profile": {
    "register": "warm-professional",
    "verbosity": "medium — bullets for status, prose for relationship-building"
  },
  "vocab_fingerprint": {
    "filler_phrases_high_frequency": ["circling back", "quick one", "to flag"],
    "filler_phrases_avoided": ["per my last email", "kindly"]
  },
  "signature_patterns": {
    "external_signoff": ["Best,\nPriya"]
  }
}
```

The `email` field is how the data-prep step identifies which messages in the corpus were authored by the persona vs. addressed to them.

## 2. Get the corpus into one schema

> 💡 **Don't have a real corpus yet?** The published [`kader-xai/priya-sft`](https://huggingface.co/datasets/kader-xai/priya-sft) dataset is a fully synthetic example — 16,779 fictional emails and meetings spanning four years of "Priya Sharma's" tenure as a Senior CSM at a fictional SaaS company. All entirely generated by deterministic Python (`scripts/generate_bulk_corpus.py` in the repo, seeded with `random.seed(42)` for reproducibility). The corpus is structured in three tiers:
>
> - **Hand-written storylines** (47 docs) — multi-document narrative arcs (Acme billing dispute, Hooli outage, Rekall churn). These are the demo backbone.
> - **Dense generated** (~15,000 docs) — per-account / per-meeting cadence. References the storylines and characters.
> - **Bulk routine** (~1,500 docs) — templated weekly syncs, status updates. Provides ambient volume so the model learns a realistic write-frequency distribution.
>
> The result: one fictional employee with 4 years of plausible mailbox history, ready to train and demo on without touching any real person's data. Use it as a template — copy `personas/priya.json`, change the fields, and run the generators with your own `accounts/` and `cast/` JSON.

Whatever your sources (Outlook PST, Gmail Takeout, Notion, Otter, Fathom, Zoom transcripts), normalize into a single JSONL:

```jsonc
{
  "doc_id": "...",
  "doc_type": "email" | "meeting_notes" | "transcript" | "rfc" | "adr" | "postmortem",
  "thread_id": "...",
  "thread_position": 1,
  "date": "ISO-8601",
  "from": {"name": "...", "email": "..."},
  "to": [...], "cc": [...],
  "subject": "...",
  "body": "...",
  "attendees": [...],
  "discussion": "...",
  "decisions": [...],
  "action_items": [...],
  "transcript_segments": [...]
}
```

Common extractors:

| Source | Tool |
|---|---|
| Outlook PST/OST | `libpst` (`readpst`) |
| Gmail | Google Takeout (.mbox) |
| Exchange / O365 | `exchangelib` or Graph API |
| Notion | Notion API → Markdown |
| Otter / Fathom / Zoom | native export → `.vtt` / JSON |

A few hundred to a few thousand of the persona's own messages is enough. Quality > quantity — filter junk, auto-replies, and bulk newsletters.

## 3. Prepare training data

`training/prep_training_data.py` does three things in one pass:

1. **Reconstruct threads** — group by `thread_id`, sort by `thread_position` then `date`. For every message authored by the persona that has prior context, the prior context becomes the input and the persona's reply becomes the target.
2. **Write SFT pairs** — chat-format `(incoming → reply)` JSONL, 95/5 train/eval split.
3. **Chunk for RAG** — every doc chunked with type-aware logic:
   - **Email**: one chunk per email (split by paragraph if > 1500 chars). Preamble has from/to/subject/date.
   - **Structured meeting notes**: one chunk per section (discussion / decisions / actions). Decisions and actions get a higher retrieval boost.
   - **Transcripts**: window of 8 segments per chunk with timestamps + speakers.
   - **RFC / ADR / design doc**: split on markdown headings.
4. **Generate the system prompt** from the persona JSON fingerprint — the model sees this every inference.

```bash
python training/prep_training_data.py --persona priya
```

For Priya: 16,779 docs in → **1,287 SFT pairs** (1,223 train + 64 eval) + **17,663 RAG chunks**.

## 4. Build the RAG index

Embed every chunk, build a FAISS index. RAG is what keeps the model honest — without it, a pure LoRA fine-tune will happily hallucinate dates and names.

```python
embedder = SentenceTransformer("BAAI/bge-base-en-v1.5")
embs = embedder.encode(texts, normalize_embeddings=True, batch_size=128)
index = faiss.IndexFlatIP(embs.shape[1])
index.add(embs.astype("float32"))
```

```bash
python training/build_rag_index.py --persona priya --batch-size 128
```

- `BAAI/bge-base-en-v1.5` → 768-dim, L2-normalized.
- `IndexFlatIP` = cosine similarity (exact search). Fine up to ~1M chunks; switch to `IndexHNSWFlat` or `IndexIVFPQ` beyond that.
- The same embedder must be used at query time.

Outputs `rag_index_<persona>.faiss` (~50 MB for ~17k chunks) and `rag_meta_<persona>.jsonl` (chunk text + provenance).

## 5. Train the LoRA

LoRA fine-tune of Qwen 2.5 7B on the SFT pairs. Unsloth gives ~2× speed and half the VRAM.

```python
model = FastLanguageModel.from_pretrained(
    model_name="unsloth/Qwen2.5-7B-Instruct-bnb-4bit",
    max_seq_length=4096,
    load_in_4bit=True,
)
model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    lora_alpha=32,
    lora_dropout=0.05,
    target_modules=["q_proj","k_proj","v_proj","o_proj","gate_proj","up_proj","down_proj"],
    use_gradient_checkpointing="unsloth",
)
```

| Hyperparameter | Value | Why |
|---|---|---|
| `r` | 16 | Rank 32 is marginally better but doubles adapter size |
| `lora_alpha` | 32 | 2× rank, conventional |
| target modules | all attention + MLP | Both matter for style |
| 4-bit base | yes | Fits 7B in ~14 GB VRAM |
